# Task 6 Brief — Initial Migration with RLS, FORCE RLS, and Grants

## Steps (verbatim from the plan, follow exactly)

**Step 1:** Apply the migration in dev mode. Prisma generates the SQL file.

```bash
cd C:\Users\Partridge\Desktop\KidsCare
pnpm --filter @kidscare/database prisma migrate dev --name init
```

This creates `packages/database/prisma/migrations/<timestamp>_init/migration.sql`. Open it.

If you get "Environment variable not found: DATABASE_URL", `.env` is missing — copy it again: `cp .env.example .env`.

**Step 2:** Append the RLS and grant statements to the END of the generated `migration.sql`. The Prisma-generated file ends with the `CREATE TABLE` blocks; append after them:

```sql
-- ─── Row-Level Security ──────────────────────────────────────
ALTER TABLE "tenants" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "tenants" FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON "tenants"
  USING (id = current_setting('app.tenant_id', true));

ALTER TABLE "users" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "users" FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON "users"
  USING ("tenantId" = current_setting('app.tenant_id', true));

-- ─── Application role grants ────────────────────────────────
GRANT SELECT, INSERT, UPDATE, DELETE ON "tenants" TO kidscare_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON "users"    TO kidscare_app;

-- ─── Auth lookup role grants (column-level) ──────────────────
GRANT SELECT (id, slug)                       ON "tenants" TO kidscare_auth_lookup;
GRANT SELECT (id, "tenantId", email, "passwordHash") ON "users" TO kidscare_auth_lookup;
```

**Step 3:** Reset and re-apply the migration to confirm it works clean (this exercises the full path: migrator role creates tables, RLS policies apply, grants execute).

```bash
pnpm db:reset
```

Expected: drop + re-create + migration apply + empty seed, no errors. The reset runs the migrator role against the test DB; if any GRANT statement fails (e.g., the role doesn't have the privilege to GRANT to another role), the whole reset fails — that's the correct safety behaviour.

**Step 4:** Verify RLS is on and policies exist.

```bash
docker exec -it kidscare-postgres psql -U postgres -d kidscare -c "\d+ tenants"
```

Expected output includes:

- `Row security: enabled, forced`
- `Policies:` section listing `tenant_isolation` with `USING` expression

**Step 5:** Verify grants.

```bash
docker exec -it kidscare-postgres psql -U postgres -d kidscare -c "SELECT grantee, privilege_type FROM information_schema.role_table_grants WHERE table_name='users';"
```

Expected: rows for `kidscare_app` with `SELECT/INSERT/UPDATE/DELETE`, and `kidscare_auth_lookup` with `SELECT`.

**Step 6:** Commit.

```bash
git add packages/database/prisma/migrations/
git commit -m "feat(database): add RLS, FORCE RLS, and three-role grants to initial migration"
```

Only stage the migration directory. The Prisma client under `packages/database/src/generated/client/` was already generated and committed in Task 5; if `prisma generate` re-ran during `prisma migrate dev`, stage any genuinely changed generated files (but typically none change for schema-only migrations).

## Constraints (binding)

- **Per Global Constraints:** every migration that creates a tenant-scoped table MUST also include `ENABLE`, `FORCE`, `CREATE POLICY`, and the `GRANT` to `kidscare_app` in the same SQL file. Splitting across migrations is a deployment hazard.
- `FORCE ROW LEVEL SECURITY` is mandatory. Without it, the migrator role bypasses policies and a misconfigured connection becomes a data breach.
- Policy expression uses `current_setting('app.tenant_id', true)` — the `true` second arg returns `NULL` instead of erroring when the setting is absent. Login flow relies on this.
- Grants are column-level on `users` and `tenants` for `kidscare_auth_lookup` — `(id, slug)` on `tenants`, `(id, "tenantId", email, "passwordHash")` on `users`. NO INSERT/UPDATE/DELETE/TRUNCATE/TRIGGER grants for this role.
- `kidscare_app` gets table-level SELECT/INSERT/UPDATE/DELETE on both tables (not column-level — the app uses the Prisma client which generates full row reads).
- Do NOT add `BYPASSRLS` to any role. If a query fails under RLS, fix the policy or the grant — do not bypass.
- Do not edit any other file in `packages/database/`; this task is migration-only.
